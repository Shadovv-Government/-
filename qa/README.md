# Проверка исходных данных и модели

Проверки охватывают исходные данные, ключи, связи и повторяемость сборки. Ответы аналитикам строятся из `core`, а диагностические запросы могут обращаться к `raw`. Основание: [задание](../project/docs/handout.md).

## Как запустить

Если окружение ещё не поднято, из корня репозитория:

```bash
cd project
bash scripts/setup.sh
```

Не выполняйте `--reset` на общей базе: параметр удаляет локальный том данных.

Аудит из каталога `project/`:

```bash
bash ../qa/run_audit.sh
```

Прочитай `qa/raw_audit.txt`. Код завершения 0 означает, что SQL выполнился, а НЕ что все проверки прошли. Скрипт выводит диагностические таблицы: решение PASS/WARN/FAIL принимается после их просмотра. Пропуски, повторения review_id и несовпадения платежей не превращаются автоматически в FAIL.

В скриптах нет изменения raw/core/mart: проверки запускаются в read-only транзакции.

## Главные договорённости

- Позиция заказа: `(order_id, order_item_id)`. Один order_item_id недостаточен.
- Платёж: `(order_id, payment_sequential)`. Несколько платежей допустимы.
- `customer_id` и `customer_unique_id` выполняют разные роли: последний нужен для подсчёта людей и повторных покупок.
- Отзывы не соединять с позициями и платежами до сведения каждого набора к нужному уровню.
- Восемь delivered-заказов с пустой датой не следует автоматически исключать из продаж из-за отсутствия даты.
- Категории не терять при JOIN: пустая категория — UNKNOWN, категория без перевода — исходное название. Все непереведённые категории сливать в UNKNOWN не нужно.
- Выручка для заданных контролей — сумма price доставленных заказов без freight_value. Средний чек для заданного контроля — сумма price + freight_value сначала на заказ, затем среднее по доставленным заказам.

Структура исходных таблиц: [raw DDL](https://github.com/daniilivanovp-droid/hackathon-students/blob/main/scripts/init/02_raw_ddl.sql). Сдаваемые контрольные ответы: [tasks.md](https://github.com/daniilivanovp-droid/hackathon-students/blob/main/docs/tasks.md).

## Неизменность raw

Снимок до сборки core, из каталога `project/`:

```bash
docker compose exec -T postgres psql -X -q -U hack -d marketplace \
  -v ON_ERROR_STOP=1 --csv < ../qa/02_raw_fingerprint.sql > ../qa/raw_before.csv
```

После запуска сборки core повтори команду с именем `qa/raw_after.csv`:

```bash
docker compose exec -T postgres psql -X -q -U hack -d marketplace \
  -v ON_ERROR_STOP=1 --csv < ../qa/02_raw_fingerprint.sql > ../qa/raw_after.csv
diff -u ../qa/raw_before.csv ../qa/raw_after.csv
```

Пустой diff означает, что число строк и диагностические отпечатки бизнес-полей совпали. Служебные поля намеренно исключены. MD5 здесь используется как практический контроль изменений, не как криптографическое доказательство.

## Проверка core

1. Изучить [контракт модели](../project/model/contract.md), команду сборки и правила преобразований.
2. Для каждой таблицы выписать, что означает одна строка; проверить PK на NULL и дубли.
3. Проверить все FK, а не только наличие ограничений в коде.
4. Сверить raw и core по ключам и денежным суммам; если число строк изменилось, потребовать объяснение каждого удаления или объединения.
5. Проверить суммы по заказам, продавцам и категориям. Нельзя довольствоваться только общим итогом: ошибка может перераспределить выручку при сохранении суммы.
6. Проверить воспроизводимость в отдельной локальной БД: raw → сборка core → снимок core → повторный запуск → повторный снимок. Для core использовать естественные ключи и бизнес-поля, исключив технические timestamps/генерируемые ID.
7. Отдельно проверить сборку с нуля на чистом core и mart. Сброс общего окружения не применять.
8. После нового блока заданий повторить аудит и пересчитать базовые показатели.

Нормализованная модель может иметь другое число строк, чем raw. Критерий — не механическое равенство всех counts, а сохранность сущностей, фактов и объяснённые преобразования.

## Результаты проверок

- Лог `raw_audit.txt` и список обнаруженных особенностей.
- Таблицу проверок core: проверка, ожидание, факт, статус, пояснение.
- Подтверждение чистой и повторной сборки с указанием команды и версии SQL.
- Список блокирующих ошибок отдельно от известных особенностей исходной выгрузки.

PASS — условие выполняется; WARN — особенность данных сохранена и объяснена; FAIL — потеря данных, дубли ключей модели, сломанные связи, неверная агрегация или невоспроизводимая сборка.
