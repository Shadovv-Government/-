## Вопрос 4

[`q4_customers.sql`](q4_customers.sql) считает из `core` **96 096 покупателей**, из них **2 997** оформили не менее двух разных заказов; доля — **3,12%**. Фактический результат: [`q4_result_pglite.csv`](q4_result_pglite.csv).

Одна строка расчёта — человек по `customer_unique_id`. Учитываются все заказы снимка, включая отменённые и недоставленные, без фильтра по дате: так получаются контрольные числа организаторов. Для текущего ответа принято считать повторные оформления по всем статусам; это допущение не означает, что все такие заказы — завершённые покупки. При пустом наборе процент будет `NULL`. Диагностика [`q4_diagnostics.sql`](q4_diagnostics.sql) показывает 99 441 записей `customer_id` и 96 096 `customer_unique_id`; человек может иметь несколько записей. Её фактический вывод: [`q4_diagnostics_pglite.json`](q4_diagnostics_pglite.json).

## Ключи, связи и QA

[`key_relationship_checks.sql`](key_relationship_checks.sql) сравнивает состав и кратность ключей всех восьми таблиц `raw` и `core` с помощью `EXCEPT ALL`, проверяет дубли и `NULL` в ключах `core`, шесть обязательных связей, наличие устойчивого идентификатора покупателя и сохранность четырёх сопоставлений связей между `raw` и `core`. Категория товара не обязана иметь перевод, платежи и отзывы не обязаны существовать для каждого заказа. Это проверка ключей и ссылок, а не сравнение всех атрибутов строк.

Фактические результаты: [`key_checks_pglite.csv`](key_checks_pglite.csv) — восемь таблиц без расхождений, дублей и пустых ключей; [`relationship_checks_pglite.csv`](relationship_checks_pglite.csv) — одиннадцать проверок, везде ноль нарушений. На отдельной временной базе искусственно удалили заказ из `raw`: проверка завершилась ошибкой. В другой отрицательной проверке создали одинаковую строку платежа в `raw` и `core` со ссылкой на несуществующий заказ, временно отключив соответствующее ограничение в тестовой базе: проверка также завершилась ошибкой. Оба изменения отменены; отпечатки `raw` после тестов совпали с исходными. При запуске через `psql -v ON_ERROR_STOP=1` ошибка SQL означает ненулевой код выхода.

Готовый аудит [`../../qa/01_raw_audit.sql`](../../qa/01_raw_audit.sql) выполнен в PGlite: удалены только управляющие команды `psql` (`\\echo`, `\\pset`, `\\timing`), SQL не менялся. Сырые наборы строк результата по порядку запросов сохранены в [`raw_audit_pglite.json`](raw_audit_pglite.json). Это диагностический вывод, не автоматический PASS всех наблюдений. Отпечатки `raw` до и после сборки совпали по всем восьми таблицам; метод из [`../../qa/02_raw_fingerprint.sql`](../../qa/02_raw_fingerprint.sql) не включает служебные поля и использует MD5 как практическую диагностику, не криптографическое доказательство.

### Запуск на базе проекта

После установки и сборки модели, из каталога `project/`:

```bash
docker compose exec -T postgres psql -X -v ON_ERROR_STOP=1 -U hack -d marketplace --csv < computer-2/q4_customers.sql
docker compose exec -T postgres psql -X -v ON_ERROR_STOP=1 -U hack -d marketplace < computer-2/q4_diagnostics.sql
docker compose exec -T postgres psql -X -v ON_ERROR_STOP=1 -U hack -d marketplace < computer-2/key_relationship_checks.sql
bash ../qa/run_audit.sh
```

Для проверки неизменности исходных данных сделать снимки до и после `bash model/build.sh` в отдельной базе:

```bash
docker compose exec -T postgres psql -X -q -v ON_ERROR_STOP=1 -U hack -d marketplace --csv < ../qa/02_raw_fingerprint.sql > computer-2/raw_before.csv
bash model/build.sh
docker compose exec -T postgres psql -X -q -v ON_ERROR_STOP=1 -U hack -d marketplace --csv < ../qa/02_raw_fingerprint.sql > computer-2/raw_after.csv
diff -u computer-2/raw_before.csv computer-2/raw_after.csv
```

Не выполняйте `--reset` на общей базе. Аудит `run_audit.sh` создаёт `qa/raw_audit.txt`; нулевой код этого конкретного аудита означает только выполнение SQL, результаты нужно изучить. Для отдельных автопроверок ключей ненулевой код означает ошибку или найденное нарушение.
