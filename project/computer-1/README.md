## Вопрос 1

Запрос `01_monthly_revenue.sql` строит календарь с сентября 2016 по август 2018 включительно. Он считает **все оформленные заказы** по дате покупки, независимо от статуса. Выручка — сумма цен товаров у заказов со статусом `delivered`, без доставки и платежей; позиции сначала агрегируются до уровня заказа. Заказ без позиций учитывается в числе заказов и даёт нулевую выручку. Пустой месяц выводится с нулями. Заказы без даты покупки в период не попадают. Суммирование игнорирует отсутствующие цены, поэтому проверяйте их наличие запросом `01_diagnostics.sql`: при пропусках выручка может быть неполной. Это явное определение числа заказов: если требуется число только доставленных заказов, его нужно согласовать и изменить фильтр.

При запущенном PostgreSQL проекта, из каталога `project/`:

```bash
docker compose exec -T postgres psql -X -v ON_ERROR_STOP=1 -U hack -d marketplace --csv < computer-1/01_monthly_revenue.sql
```

Если задан `DATABASE_URL` и установлен `psql`, запрос можно выполнить так:

```bash
psql -X -v ON_ERROR_STOP=1 "$DATABASE_URL" --csv -f computer-1/01_monthly_revenue.sql
```

Запрос `computer-1/01_diagnostics.sql` выполняется аналогично и показывает количество пропусков и независимую сумму. Контроль организаторов — 24 строки и выручка 13 221 498.11. Результаты должны быть повторно получены из `core` на целевом PostgreSQL 16.

### Фактический запуск 28 октября 2026 года

Исходные восемь CSV взяты из официального репозитория Olist на коммите `d9e49802f3e92d09ee94ab9ccc5e457f207a8959`. База и `core` собраны локально в PGlite 0.5.12 с PostgreSQL 18.6; итог запроса из `core` сохранён в `01_monthly_revenue.csv`.

- Получено 24 строки, 99 421 заказ за период и 13 221 498.11 товарной выручки. Ноябрь 2016 года — месяц без заказов и выручки.
- В периоде 96 478 доставленных заказов; заказов без даты покупки во всей модели и позиций доставленных заказов без цены в периоде не обнаружено. Результат `01_diagnostics.sql` сохранён в `01_diagnostics_pglite.csv`.
- При двух последовательных сборках отпечатки всех восьми таблиц `core` совпали; результаты — в `core_fingerprint_pglite.csv`. Отпечатки `raw` до и после также совпали.
- В отдельный исходный набор добавлен дубликат заказа: сборка завершилась ошибкой ключа, а после отката все восемь отпечатков прежнего `core` сохранились. Это проверка на временной базе PGlite, не изменение общей `raw`.

Docker и `psql` на компьютере 1 не обнаружены. Установка организаторов, запуск через Docker и чистая и повторная сборка на целевом PostgreSQL 16 пока **не проверены**. Положительный результат PGlite не подтверждает их работу.

## Проверка двух сборок

Используйте отдельную локальную базу с уже загруженным `raw`, без зависимых объектов в `core`. Сборка пересоздаёт таблицы `core` и не использует `CASCADE`. Из каталога `project/` после `bash scripts/setup.sh`:

```bash
bash model/build.sh
docker compose exec -T postgres psql -X -q -v ON_ERROR_STOP=1 -U hack -d marketplace --csv < computer-1/core_fingerprint.sql > computer-1/core_before.csv
bash model/build.sh
docker compose exec -T postgres psql -X -q -v ON_ERROR_STOP=1 -U hack -d marketplace --csv < computer-1/core_fingerprint.sql > computer-1/core_after.csv
diff -u computer-1/core_before.csv computer-1/core_after.csv
```

Пустой diff означает совпадение количества строк и отпечатков всех полей в восьми таблицах. Компьютер 2 отдельно сравнивает отпечатки `raw` до и после сборки. Не запускайте `--reset` на общей базе; проверки целевого PostgreSQL 16 должны быть зафиксированы с датой, версией и фактическими результатами.
