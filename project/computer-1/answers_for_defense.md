# Ответы на вопросы кейса

Это шпаргалка для объяснения. Числа ниже рассчитаны из `core` на исходных CSV в PGlite 0.5.12 / PostgreSQL 18.6. Для окончательной сдачи их нужно сверить с SQL и результатами компьютеров 2–4 и повторить на целевом PostgreSQL 16. Вопросы 6–10 организаторы ещё не опубликовали.

## 1. Выручка и число заказов по месяцам

За период с сентября 2016 по август 2018 года получилось **24 месяца**, **99 421 оформленный заказ** и **13 221 498,11 товарной выручки**. В ноябре 2016 года не было заказов: этот месяц присутствует в отчёте с нулями. Помесячные результаты находятся в [01_monthly_revenue.csv](01_monthly_revenue.csv).

**Как считали:** месяц определяли по дате покупки. В числе заказов учтены все статусы, в выручке — только `delivered`. Выручка — сумма цен товаров без доставки и платежей. Сначала суммировали позиции каждого заказа, чтобы количество заказов не увеличилось из-за нескольких позиций. Определение числа заказов нужно согласовать: организаторы могут ожидать только доставленные заказы.

## 3. Средний чек

Средний чек доставленного заказа с позициями — **159,88**. В среднем на такой заказ приходится **1,14 строки и 1,14 товарной единицы** после округления.

**Как считали:** сначала сложили цену товаров и стоимость доставки всех позиций внутри каждого доставленного заказа, затем усреднили полученные суммы по заказам с позициями. В этом источнике одна строка позиции соответствует одной товарной единице, поэтому два средних количества совпадают. Если усреднять отдельные позиции, получится другая метрика, а не чек заказа.

## 4. Покупатели и повторные покупки

В данных **96 096 уникальных покупателей**. Из них **2 997** оформили не менее двух разных заказов — **3,12%**.

**Как считали:** использовали `customer_unique_id` как идентификатор человека и считали разные `order_id` по всем статусам. `customer_id` для этого не подходит: он обозначает запись покупателя, которая может отличаться от заказа к заказу. Процент — число покупателей с двумя и более заказами, делённое на общее число покупателей.

## 5. Выручка по категориям

Крупнейшая категория — `beleza_saude` («красота и здоровье»), её товарная выручка составила **1 233 131,72**, или примерно **9,33%** от общей товарной выручки. По контрольным данным QA получается **74 группы категорий**, включая группу с незаполненной категорией; их сумма должна составлять **13 221 498,11**.

**Как считали:** складывали цены позиций доставленных заказов по исходной категории товара, без доставки. Товары с пустой категорией оставляем отдельной группой; товары, у которых категория есть, но нет перевода, сохраняем под исходным названием. Результаты по всем категориям и их доли для окончательной сдачи нужно сверить с компьютером 4.

## Короткие ответы на возможные вопросы защиты

- **Почему нельзя соединить позиции, платежи и отзывы сразу?** У заказа может быть несколько строк в каждой таблице. Прямое соединение перемножит строки и исказит суммы. Сначала агрегируем каждый набор до общего уровня.
- **Почему `customer_unique_id`, а не `customer_id`?** Первый связывает записи одного человека между заказами, второй может меняться для разных заказов.
- **Почему выручка и средний чек считаются по-разному?** В контрольной выручке задана цена товаров без доставки, а контрольный чек включает цену товаров и доставку на уровне заказа.
- **Почему не удалили строки с пропусками?** Пропуск — особенность исходных данных. Если удалить строки без категории или перевода, часть товаров и выручки исчезнет из анализа.
- **Что доказала повторная сборка?** В PGlite две сборки на одном наборе дали одинаковые отпечатки восьми таблиц, а `raw` не изменился. При ошибке ключа транзакция сохранила предыдущую модель.
- **Проверено ли всё на целевой базе?** Нет. Расчёты и проверка повторной сборки выполнены в PGlite с PostgreSQL 18.6; штатный запуск на PostgreSQL 16 через Docker ещё нужно выполнить.
