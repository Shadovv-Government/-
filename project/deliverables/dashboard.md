# Концепция дашборда: «Продажи и исполнение заказов Capibara»

Дашборд не собирается, описываем концепцию. Область — **продажи и качество исполнения**: сколько продали, кому, в каких категориях и как это дошло до покупателя. Цифры в примерах — фактические значения из `core` на исходной выгрузке (до вброса), они пересчитываются после обновления данных.

## Аудитория и решения

| Кто смотрит | Решение, которое принимает | Какие блоки |
|---|---|---|
| Коммерческий директор | Куда направить маркетинг и привлечение продавцов; растёт ли бизнес | Динамика выручки и заказов, категории, регионы |
| Категорийные менеджеры | Какие категории развивать, где расширять ассортимент; что делать с неразмеченными товарами | Категории, доля `UNKNOWN`, продавцы |
| Операционный менеджер | Где срывается доставка, с какими продавцами и регионами разговаривать | Срок доставки, доля просроченных, отмены |
| CRM/удержание | Нужны ли программы возврата покупателей | Покупатели, доля повторных |

## Показатели

Единая договорённость: **выручка = сумма `price` позиций заказов со статусом `delivered`, без доставки** (контроль 13 221 498.11). Если показатель использует другой состав суммы, это сказано в формуле.

| Показатель | Формула | Уровень расчёта | Источник в `core` | Складывается по срезам? |
|---|---|---|---|---|
| Выручка (товары) | `SUM(price)` по позициям delivered-заказов | Позиция `(order_id, order_item_id)` | `order_items` + `orders.order_status` | Да — по месяцам, категориям, продавцам, регионам |
| Доставка | `SUM(freight_value)` по тем же позициям | Позиция | `order_items` | Да; но не смешивать с выручкой товаров |
| Заказы | `COUNT(DISTINCT order_id)` | Заказ | `orders` (+ `order_items` для среза по категории/продавцу) | **Нет** по категориям и продавцам: заказ может содержать несколько категорий и продавцов (сумма заказов по категориям 97 276 против 96 478 заказов) |
| Средний чек | `SUM(price+freight_value) / COUNT(DISTINCT order_id)` — сначала сумма на заказ, затем среднее (контроль 159.88) | Заказ | `order_items`, `orders` | **Нет**. При укрупнении пересчитывать как отношение сумм, а не среднее средних. По категории чек — не свойство заказа |
| Позиций на заказ | `COUNT(*) позиций / COUNT(DISTINCT order_id)` | Заказ | `order_items` | Нет (отношение) |
| Уникальные покупатели | `COUNT(DISTINCT customer_unique_id)` через `orders → customers` | Человек | `customers`, `orders` | **Нет**: один человек покупает в разных месяцах, категориях и штатах (в delivered 93 358 человек против 95 789 при сумме по категориям). `customer_id` для этого не годится — он меняется от заказа к заказу |
| Доля повторных покупателей | покупатели с ≥2 заказами / все покупатели (контроль 3.12 %, 96 096 покупателей) | Человек | `customers`, `orders` | **Нет**. Зависит от окна наблюдения: ранние когорты «успели» вернуться, поздние нет. Показывать по когортам первой покупки |
| Доля категории | `выручка категории / общая выручка` | Позиция → категория | `order_items`, `products`, `category_translations` | В пределах среза — 100 %; средние доли по месяцам не усреднять |
| Срок доставки, дни | `AVG(order_delivered_customer_date − order_purchase_timestamp)` | Заказ | `orders` | Нет (среднее; при укрупнении — взвешенное по числу заказов). 12.6 дня в среднем |
| Доля просроченных | заказы с `delivered_customer_date > estimated_delivery_date` / delivered с датой вручения | Заказ | `orders` | Нет (отношение). 8.11 % |
| Средняя оценка | сначала среднее оценок на заказ, затем среднее по заказам | Заказ (отзывы 1:N) | `order_reviews` | Нет. 4.09 |
| Доля отмен и недоступных | `(canceled + unavailable) / все заказы` | Заказ | `orders` | Нет (отношение) |

## Срезы

- **Время** — по месяцу оформления (`order_purchase_timestamp`). Месяцы строить по календарной оси: в данных нет заказов за ноябрь 2016, без оси он пропадёт из графика вместо нулевой точки. Крайние периоды (сентябрь–октябрь 2016, сентябрь–октябрь 2018) неполны: 4, 324 и 16, 4 заказа — помечать на графике.
- **Категория** — английское название, fallback — исходное, пустая — `UNKNOWN`; показывать `UNKNOWN` отдельной строкой, а не скрывать (1.29 % выручки).
- **Продавец** — город и штат продавца; выручка продавца считается только по его позициям.
- **Регион покупателя** — штат записи `customers` заказа.
- **Статус заказа** — для воронки (создан → одобрен → отгружен → доставлен / отменён).

## Источники и ограничения

- Только `core` (при необходимости витрины `mart`); `raw` дашборд не читает.
- Платежи — отдельный факт. Выручку, чек и категории нельзя разрезать по типу оплаты: соединение позиций с платежами и отзывами без предварительной агрегации размножает суммы. Платежи показывать отдельным блоком (по заказам), сумма платежей ≠ выручка (по данным QA в 366 сопоставимых заказах расхождение больше 0.01 — нужна отдельная политика, а не подгонка).
- Заказы без позиций (775) попадают в статусную воронку, но не в выручку. Delivered без даты вручения (8) входят в выручку, но не в срок доставки и долю просроченных.
- Отгрузки по продавцам источник не содержит: даты отгрузки и вручения — на уровне заказа. Срок доставки по продавцу нельзя считать честно для заказов с несколькими продавцами; в разрезе продавца показывать только как «заказы, где он участвовал».
- Источник — снимок: истории изменений статусов и адресов нет, динамику «как было на дату» не показывать. Часового пояса в данных нет.
- Валюта в данных не указана; в подписях писать «в валюте источника».
- После вброса значения и контроли пересчитать; формулы остаются, пока вброс не изменит определения.

## Раскладка (эскиз)

1. Верхняя полоса: выручка, заказы, средний чек, покупатели, доля повторных — с периодом и признаком неполного периода.
2. Динамика по месяцам: выручка (столбцы), заказы (линия), календарная ось.
3. Категории: рейтинг по выручке и доле, `UNKNOWN` отдельно.
4. Исполнение: срок доставки, доля просроченных, оценка, отмены — по штату покупателя.
5. Продавцы: топ по выручке, штат, число заказов и единиц товара.
